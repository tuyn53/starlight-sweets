## 1. 根因分析：为什么"画得快却感觉卡"

### 1.1 帧调度缺陷（已确认存在，病因推测）

`main.js` 有两个独立的动画循环，都永不停止：

```js
// 主循环
requestAnimationFrame(frame);          // main.js:18 / 194
// 首页骨骼动画循环
if (homeRigs.length) requestAnimationFrame(homeFrame);  // main.js:229
```

`homeFrame`（main.js:208-229）即使首页隐藏也会每帧执行：
- `if (!r.cv.offsetParent) continue;` —— **`offsetParent` 读取会强制同步布局(reflow)**，移动端主线程昂贵操作
- 末尾 `Rig.setCtx(document.getElementById('game').getContext('2d'))` —— 每帧 DOM 查询 + getContext

两个 rAF 回调在同一帧被浏览器依次调用，等于主线程每帧要跑两套逻辑。这是"帧率上不去 + 偶尔顿一下"的高置信结构原因。

### 1.2 输入采样节奏（已确认存在，是否致"跟不上手"待验证）

- 触屏：`pointermove` 更新 `joy.dx/dy`（core.js:166-172）
- 采样：`update()` 里每固定步长读一次 `Input.vector()`（logic.js:354）
- 帧率 60Hz、触控采样可能 120Hz+，中间无缓冲队列；掉帧时输入到画面的延迟被放大

### 1.3 GPU 合成侧（未测，不臆断）

探针用 `performance.now()` 包 `drawImage`，测的是 JS 提交绘制命令的 CPU 时间。**Canvas 的实际像素光栅化/合成发生在 GPU 或合成线程，这段没进数字**。老大拒绝跑 raf-probe，所以这一侧保持"未知"，用 P2 保守覆盖。

## 2. 施工单（按优先级，每项带影响面 + 验证法）

> 纪律：判定层/架构层改动先说明影响面；实现层 bug 直接给修法。每改一项验证一项，不批量铺开。

### P0 · 消灭双 rAF 常驻（架构层，影响面已说明，待确认后动手）

**改什么**：把 `homeFrame` 合并进主循环，或让它在非首页时真正停止（而非仅跳过绘制）。

**影响面**：
- 涉及 `main.js` 的 `frame()` 与 `homeFrame()`，以及首页 canvas 动画。
- 不改任何玩法逻辑、数值、判定。
- 风险：合并后首页动画时序可能变化，需回归首页视觉。

**推荐做法**：保留两个函数，但用单一 rAF 驱动——在 `frame()` 末尾按状态决定是否调用 `homeFrame` 的绘制部分，删掉 `homeFrame` 自己的 `requestAnimationFrame`。这样全局只有一个 rAF 源。

**验证法**：改前改后在同一台手机上跑 `scripts/raf-probe.html` 的空闲模式 10 秒，对比 p95 帧间隔。⚠️ 老大拒绝跑探针——若坚持不测，只能靠"主观流畅度"验证，这也接受，但结论强度降为 L1。

### P0-b · 去掉每帧 `offsetParent` 强制布局（实现层，直接修）

**改什么**：用状态标志代替 `offsetParent` 查询。

```js
// 改前（每帧强制 reflow）
if (!r.cv.offsetParent) continue;
// 改后：用 game.state 或缓存的可见性标志
if (game.state !== 'menu') continue;   // 首页动画只在 menu 状态跑
```
并在状态切换时刷新标志，避免查询 DOM 布局属性。

**影响面**：仅首页动画显示时机；无玩法影响。风险低。

**验证法**：进游戏后首页 canvas 不再绘制（符合预期），主观顿挫是否减少。

### P1 · 输入采样补偿（手感层，需老大拍板）

**改什么**：给虚拟摇杆加"最新值即时生效"——`pointermove` 里除了更新 `joy.dx/dy`，直接在下一次 update 用最新值（当前已是如此）；真正能改善"跟不上手"的是：
1. **降低固定步长延迟**：`CFG.STEP=1/60` → 输入延迟上限 16.7ms，如果掉到 30fps 则 update 一帧补多步，延迟反而来自渲染。
2. **加大摇杆灵敏度/移动速度**：这不是 bug 是手感参数，`CFG.BASE.speed=195`。"跟不上手"很可能就是速度偏慢，_CPU 没问题_。
3. **触摸目标与视觉反馈**：摇杆中心跟随手指，已实现。

**需老大决定**：你要的"跟手"是①反应延迟更低（改输入系统，风险中）还是②角色移动更快（改 `speed` 数值，风险低，一行）？**先确认这个再动手**——否则又是猜。

### P2 · GPU 侧保守降级（可选，未确诊）

**改什么**（保守，效果可逆）：
- `core.js:7` DPR 上限 `Math.min(dpr, 2)` → 低端机可降到 1.5（需加设备判断，或做成设置项）
- 这是"降分辨率换帧率"，会让画面略糊

**影响面**：全画面清晰度。风险：视觉降级，老大可能不接受。

**验证法**：必须真机对比，否则不做。既然 GPU 侧未测，**这项默认不实施**，仅登记为备选。

## 3. 明确不做的（基于证据否决）

| 不做 | 理由（证据） |
|---|---|
| ❌ 换游戏引擎 | 探针证明绘制 0.84ms ≪ 16.7ms；换引擎不解决帧调度缺陷，且重写成本巨大 |

| ❌ 给经验球渐变做缓存（H1） | 同上，60 球渐变不是瓶颈，改了也测不出差异 |
| ❌ 一次全改四项 | 违反单变量释放，出问题无法归因 |
