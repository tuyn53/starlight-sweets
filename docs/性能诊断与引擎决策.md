# 甜星大作战 · 性能诊断与"要不要换引擎"决策

> 触发：老大反馈"玩起来卡卡的，最新款手机应该不是性能问题，要不要换游戏引擎"。
> 方法：performance-optimization skill（set budget → measure → find the one bottleneck）。
> 状态：**引擎决策已定（不换）；渲染提交侧假设已被真机数据证伪；真因待定**。最后更新 2026-11-19。
>
> **2026-11-19 真机数据更新（老大的手机 390×699 / DPR3→渲染用2）**：满屏 80怪+60球 纸娃娃平均 **0.84ms**（p95 2ms，max 4ms），单图 0.39ms，中载 0.45ms。全部远低于 16.7ms 预算。**H1（渐变）/ H2（骨骼 draw call）假设证伪——绘制指令本身不是瓶颈**。注意该探针测的是 CPU 提交时间（performance.now 包住 drawImage），未覆盖 GPU 光栅化/合成与真实 rAF 帧间隔。老大拒绝再跑第二个 raf-probe，故 GPU 侧保持"未测"。

---

## 0. 结论先行：不换引擎

**换引擎解决不了这类卡顿，还会引入巨大风险。** 理由三条，都是硬事实：

1. **瓶颈不在引擎层。** 这是纯 Canvas 2D + Web Audio 的 H5，没有场景图、没有物理引擎、没有材质系统。换 Godot/Unity 后，你依然要在移动端 WebView 或导出包里画同样的 80 只怪、同样的经验球渐变——draw call 数量和填充率不会因为你换引擎就消失。
2. **"最新款手机不该卡"是错误前提。** 移动端浏览器的 Canvas 2D 主要是软件光栅化，瓶颈在每帧 draw call 数 + 填充率 + GC，跟 SoC 算力关系有限。skill 原话：*"fill-rate bound → lower render resolution；overdraw → fewer large transparent layers"*。iPhone 17 上跑微信内置浏览器，Canvas 2D 一样会卡。
3. **代价远大于收益。** 项目核心卖点是"零依赖、零构建、浏览器打开就玩"（README 第 3 行），49→71 项测试、`slicerig` 纸娃娃、程序化 BGM 全绑在原生 JS 上。换引擎 = 全部重写 + 引入构建链 + 放弃 H5 即开即玩，而换来的是一个**未经证实的性能改善**。

**决策契约（decision-and-evidence）：**
```yaml

current_default_action: "换引擎（老大提议）"

  - "探针平均帧时 <16.7ms → 不是性能问题，是手感/节奏问题（回到节奏方案）"

  - "两者都慢 → 填充率/渐变/GC 瓶颈，做批量化与离屏缓存"
information_costs: "极低：一个 HTML 探针页，用户手机跑 3 秒"

```

## 1. 把"卡"变成数字（skill 第 1 步）

- 预算：60 FPS = 16.67ms/帧；30 FPS = 33.3ms/帧。移动端建议留 20-30% 余量应对发热降频。
- 可复现 worst case：满屏 80 敌人 + 60 经验球（`CFG.SPAWN.targetCap=80`，符合我们的维持数量模型上限）。
- **测量工具**：`scripts/perf-probe.html` —— 用手机浏览器打开，点"开始测量"，它会跑 180 帧模拟绘制，输出平均/p50/p95/最大帧时。请把结果截图发我。
- 这台机器没有浏览器自动化工具（agent-browser/chromium/playwright 均无），**我无法代替你在真机上测**。所有下面的候选瓶颈都 labeled `hypothesis`，未经测量不得当成结论。

## 2. 代码静态审计：候选瓶颈（按可疑度排序，均为 hypothesis）

| # | 候选瓶颈 | 代码位置 | 每帧量级 | 为什么可疑 |
|---|---|---|---|---|
| H1 | 经验球每帧新建径向渐变 | `render.js:151` drawGems | 满屏 60 球 = 60 个 `createRadialGradient`/帧 | skill 明确列为 per-frame allocation → GC 周期性卡顿；且渐变填充贵 |
| H2 | 纸娃娃切片每帧多次 drawImage | `slicerig.js:76-87` | 每怪 5 drawImage + 10 状态变换；80 怪 = 400 drawImage/帧 | draw call 数量是移动端 Canvas 第一杀手 |
| H3 | 静态场景每帧全量重绘 | `render.js:80-142` drawScene | 每帧 ~20-30 装饰 × (Math.sin + save + 多路径) | 地面/网格/装饰是静态的，可离屏缓存成一张图 |
| H4 | 资源物/宝箱每帧渐变 | `render.js:165,186` | 少量（<10）| 量级小，优先级低 |
| H5 | 双 rAF 循环并存 | `main.js:18,227` | `homeFrame` 每帧读 `offsetParent` | 首页隐藏时跳过绘制，开销小，但属结构隐患 |
| H6 | 震屏旋转整屏 | `render.js:7-9` | 每帧一次 rotate（全画面） | 有 `shakeScale` 开关，量级中等 |

**已排除的假阳性**：`orb()` 定义了但从未调用（`grep -c` 显示只有定义），不是热点——这正是"先查再改"避免的误判。


拿到数字后，按归因结果选最小修复（**每轮只放 1 个变量**）：

| 若主瓶颈是 | 修复杠杆（单次一个） | 预期效果 | 风险 |
|---|---|---|---|
| H1 渐变/GC | 经验球的辉光渐变预渲染成小 sprite，drawImage 代替每帧 createGradient | 省 60 次/帧对象创建 | 低，纯渲染层 |
| H2 纸娃娃 draw call | 低性能档自动关 `USE_SLICE`，退回单 drawImage 的程序化绘制；或给怪物做"简化骨骼"（只摆腿不摆臂） | draw call 400→80/帧 | 中，影响画风表现，需老大拍板 |
| H3 静态地面 | `drawScene` 的装饰层离屏缓存到 offscreen canvas，仅相机移动时重绘 | 省每帧 ~30 组路径 | 低，视觉不变 |
| H6 震屏 | 已有关闭开关；若仍卡可在低端机默认降低 shakeScale | 省一次全屏 rotate | 低 |

## 4. 迁移检查与红线

- `near`：同类绘制（道具/宝石/宝箱）的渐变都要一起核查，别只修宝石。
- `medium`：`USE_SLICE` 关掉会影响 `homeFrame` 首页骨骼动画，需确认回退路径（`Rig.draw`）正常。
- `far`：这些优化是 Canvas 2D 通用手法，可迁移到其他 H5 项目。
- `negative_transfer`：离屏缓存占内存，移动端要控制缓存尺寸；降 DPR 会让画面变糊，需权衡。

**红线**：任何优化后必须重测同一探针三次，取平均与 p95，三次都改善才保留；否则回滚。禁止"看着流畅了就算赢"。
